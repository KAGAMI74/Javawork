## 三、核心代码讲解（约 90 秒，重点）

### 3.1 字段设计与 `Serializable`

【代码】`LostItem.java` 第 13–30 行

```java
public class LostItem implements Serializable {
    private static final long serialVersionUID = 1L;
    private final long id;
    private final ItemType type;
    private final String title;
    private final String location;
    private final String contact;
    private final Date publishTime;
    private ItemStatus status;
    private String claimant;
    private Date claimTime;
```

【讲稿】
"三个设计点：

**第一，实现 `Serializable`。** 因为我们不用数据库，而是把'内存集合 + 对象序列化快照'作为持久化方案，同时这个对象还要通过 Socket 从客户端传到服务端。两个场景都要求可序列化。

**第二，`serialVersionUID` 固定为 `1L`。** 这是给反序列化兜底的：如果类结构变了而版本号也变了，读旧快照文件会直接抛 `InvalidClassException`。固定成 `1L`，我们删字段时旧数据文件仍能读，只是新字段为空。

**第三，字段分两类。** 前六个是 `final`，记录一旦建立就不该被改——物品名称、地点这些改了就变成另一条记录了；后三个 `status`、`claimant`、`claimTime` 不是 `final`，因为它们正是**认领操作要修改的状态**。这种'不可变部分 + 可变状态'的分法，让字段的修改权限一目了然。"

> 追问预案：为什么 `Date` 字段不直接用 `final` 的不可变对象？
> 答："`Date` 本身是可变类，我用它的 `final` 引用只是保证引用不换、不保证内容不变。所以在 getter 里做了防御性拷贝（见 3.4），把可变内部状态封住。"

### 3.2 构造器校验 `clean()`

【代码】`LostItem.java` 第 40–55 行

```java
public LostItem(long id, ItemType type, String title, String location, String contact, Date publishTime) {
    this.id = id;
    this.type = type;
    this.title = clean(title, "物品名称");
    this.location = clean(location, "地点");
    this.contact = clean(contact, "联系方式");
    this.publishTime = publishTime == null ? new Date() : new Date(publishTime.getTime());
    this.status = ItemStatus.OPEN;
}

private static String clean(String value, String fieldName) {
    if (value == null || value.trim().isEmpty()) {
        throw new IllegalArgumentException(fieldName + "不能为空");
    }
    return value.trim();
}
```

【讲稿】
"这段是我认为最值得讲的设计——**把数据校验放在实体类的构造器里，而不是放在业务层。**

好处有两个：一是**不可能构造出非法的记录**，只要对象存在就一定是合法的，业务层不用反复判空；二是**错误信息带字段名**，`clean(value, "地点")` 里传入字段名，报错会精确到哪个字段没填，客户端能直接把 `IllegalArgumentException` 的 message 返回给用户。

另外 `clean()` 顺手做了 `trim()`，用户多敲的空格会被去掉。这一行还体现了**小函数的复用**：三个字段共用一套校验逻辑，以后加字段直接调 `clean()` 就行。

最后一行 `this.status = ItemStatus.OPEN`：新发布的记录初始状态一定是待认领，不允许外部指定，这也是把默认值规则收进实体的做法。

**这里本来还有一个描述字段**，`description`，我们组讨论后取消了——原因是它的使用频率很低，却让列表每条记录占两行、信息密度变低。取消后列表变成单行展示，发布时要输入的项也从五项减到四项。"

### 3.3 `claim()` 状态流转（关键，务必讲清）

【代码】`LostItem.java` 第 62–70 行

```java
public synchronized boolean claim(String claimer) {
    if (status == ItemStatus.CLAIMED) {
        return false;
    }
    this.claimant = clean(claimer, "认领人");
    this.claimTime = new Date();
    this.status = ItemStatus.CLAIMED;
    return true;
}
```

【讲稿】
"这是整个实体类里**唯一会改变状态的方法**，也是我们修过一个真实 bug 的地方。

设计上，我把'状态判断 + 状态修改'三行代码放进同一个方法、并加 `synchronized`，保证对同一条记录的认领是**原子操作**。

为什么必须这么做？我们测试时发现：两个客户端几乎同时认领同一条记录，两个都提示'认领成功'，后一个把前一个的认领人覆盖掉了。原因是原来的代码里'判断是否已认领'和'写入认领人'是分开的两步——线程 A 判断完还没写，线程 B 也判断到'待认领'，两个都写入了。

修法是两步：一是把判断和写入合并进这一个 `synchronized` 方法，锁的粒度是**单条记录**（`this`），不同记录之间互不影响，不影响并发性能；二是让方法返回 `boolean`，业务层根据返回值返回'认领成功'或'该物品已经被认领，不能重复认领'。**用返回值表达失败原因，比抛异常更轻，也更贴合这个业务场景。**

这里也顺便说明了我们项目的线程安全分工：`repository` 层用 `ConcurrentHashMap` 保证'不同记录的并发访问'安全，`model` 层用 `synchronized` 保证'同一条记录的状态流转'安全——两层各管一段，不重复加锁。"

### 3.4 `DateTimeFormatter` 与防御性拷贝

【代码】`LostItem.java` 第 19–20 行、57–60 行、108–122 行

```java
private static final DateTimeFormatter DATE_FORMAT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
private static final ZoneId ZONE = ZoneId.systemDefault();

private static String format(Date date) {
    return date == null ? "" : DATE_FORMAT.format(date.toInstant().atZone(ZONE));
}

public Date getPublishTime() {
    return new Date(publishTime.getTime());   // 防御性拷贝
}

public Date getClaimTime() {
    return claimTime == null ? null : new Date(claimTime.getTime());
}
```

【讲稿】
"这里讲两个细节。

**第一，时间的格式化器为什么不用 `SimpleDateFormat`。** 我最初写的是 `SimpleDateFormat`，后来改成 `DateTimeFormatter`。原因是我们是**多线程服务端**，每个客户端连接由一个线程处理；`SimpleDateFormat` 内部持有一个可变的 `Calendar`，多个线程共用一个静态实例时，格式化结果会串错、甚至抛出数字解析异常。而 `DateTimeFormatter` 是不可变对象，官方说明它就是设计成线程安全的，可以放心作为 `static final` 被所有线程共享。这是一个真实存在的并发陷阱，我把它作为测试项写进了报告。

因为 `Date` 是旧 API，`DateTimeFormatter` 只认 `TemporalAccessor`，所以中间加了一步 `date.toInstant().atZone(ZONE)` 做桥接——这也是新老时间 API 混用时的标准写法。

**第二，getter 里的防御性拷贝。** `getPublishTime()` 返回的是 `new Date(publishTime.getTime())` 而不是字段本身。因为 `Date` 是可变的，如果直接把内部对象交出去，调用方一句 `setTime()` 就能绕过我的校验改掉发布时间。返回副本，就把实体的内部状态保护起来了——这是封装该有的样子。"

### 3.5 `matches()` 与 `toDisplayText()`

【代码】`LostItem.java` 第 76–86 行、124–131 行

```java
public boolean matches(String keyword, String typeValue, String statusValue) {
    String normalizedKeyword = keyword == null ? "" : keyword.trim().toLowerCase();
    boolean keywordMatched = normalizedKeyword.isEmpty()
            || title.toLowerCase().contains(normalizedKeyword)
            || location.toLowerCase().contains(normalizedKeyword);
    boolean typeMatched = typeValue == null || typeValue.trim().isEmpty()
            || type.name().equalsIgnoreCase(typeValue.trim());
    boolean statusMatched = statusValue == null || statusValue.trim().isEmpty()
            || status.name().equalsIgnoreCase(statusValue.trim());
    return keywordMatched && typeMatched && statusMatched;
}

public String toDisplayText() {
    String claimedText = status == ItemStatus.CLAIMED
            ? "，认领人：" + claimant + "，认领时间：" + format(claimTime) : "";
    return String.format("[%d] %s | %s | %s | 地点：%s | 联系：%s | 发布时间：%s%s",
            id, type.getDisplayName(), status.getDisplayName(), title, location, contact,
            format(publishTime), claimedText);
}
```

【讲稿】
"`matches()` 是条件查询的判断逻辑，三个参数都是可选条件，留空表示不限，条件之间是'与'的关系。关键词同时匹配**物品名称和地点**——这样查'图书馆'能找到所有在图书馆的记录，比只匹配名称实用。`toLowerCase()` 让搜索大小写不敏感，提升体验。

把匹配逻辑放在实体自己的方法里，好处是 `service` 层只需要一行 `if (item.matches(...))`，不用写一堆字段判断——**把'数据'和'对数据的判断'放在一起**，这是面向对象的常规做法，也叫信息专家模式。

`toDisplayText()` 是列表和详情共用的展示文本。两点：一是取消描述字段后，这里就是**单行展示**，形如 `[6] 招领 | 待认领 | 黑色钱包 | 地点：图书馆三楼 | 联系：王同学 13900000000 | 发布时间：…`；二是已认领的记录会在末尾拼接认领人和认领时间，用 `claimedText` 变量先算好再拼，避免在 `String.format` 里写三目运算符导致可读性下降。

这里用到的 `String.format` 和 `String` 的各种方法，也正好对应要求里'用到了常用类'这一项。"

## 四、测试与缺陷复现（约 40 秒）

【讲稿】
"这一部分是我另一个主要职责——不只跑一遍流程，而是**记录缺陷、定位原因、验证修复**。我按 `client_input.txt` 做全流程回归，一共发现并推动修复了 5 个问题，其中三个比较典型：

| # | 现象 | 定位到的原因 | 修复 |
| --- | --- | --- | --- |
| 1 | 客户端 `readObject` 一直阻塞，程序假死 | 两端都先创建输入流等对方发流头，互相等待形成**死锁** | 建立输出流后立即 `flush()` |
| 2 | 同一条记录被两个客户端认领，后一个覆盖前一个 | `claim()` 里判断与写入不是原子操作，且未加锁 | 合并进 `synchronized` 方法并校验状态 |
| 3 | 控制台显示正常，输出重定向到文件后中文变乱码 | Windows 下 JVM 默认按 GBK 编码控制台输出 | 运行参数加 `-Dstdout.encoding=UTF-8` |
| 4 | 统计要多次全表遍历 | 6 个指标各查一遍 | 改为一次遍历累加 |
| 5 | 列表每条记录占两行、信息密度低 | 描述字段使用频率低 | 取消描述字段，改单行展示 |

【讲稿】重点讲第 1 个：
"第 1 个最典型。现象是客户端启动后卡住不动。原因在 Java 对象流的约定：`ObjectInputStream` 创建时会先等待对方的**流头**（一个序列化魔数），双方都先建输入流、都在等对方发流头，就谁也不往下走。修法是在建完输出流后立刻调 `flush()`，把流头先发出去。这个问题在本地单机测试时不容易发现，我们后来用两个客户端同时连才稳定复现。

第 2 个问题的验证结果在运行输出里，第七条记录被认领一次成功、第二次提示 `[失败] 该物品已经被认领，不能重复认领`——这条输出我保留在答辩材料里，可以直接演示。

**测试方法上**，我写了 `client_input.txt` 把菜单操作顺序固定下来，这样每次回归只要重定向输入就能复现整条流程，不用手敲；输出重定向到文件也都是 UTF-8，便于比对。这套脚本现在就放在源码包里，也体现了'可重复的测试'这个要求。"

> 追问预案：为什么不用 JUnit？
> 答："这个作业的重点是 C/S 与序列化、反射，交互过程本身就跨进程跨网络，用例脚本按真实操作顺序回放更贴近实际；另外课程也没要求引入测试框架。用输入脚本 + 输出比对，成本低而且能覆盖跨进程场景。"

## 七、预计追问与参考回答

**Q1：你们为什么不用数据库？**
A：作业要求是从七项技术里选 3–5 项，我们选了集合、反射、序列化、多线程、网络通信这 5 项，数据库没有选。持久化我们用'内存集合 + 对象序列化快照'替代：`ConcurrentHashMap` 保证运行期并发安全，服务端每 45 秒自动把快照写到 `.dat` 文件，重启后能恢复。这样也顺便把序列化这个技术点用实在了。

**Q2：为什么用短连接，不做长连接？**
A：客户端每次操作建立连接、收发一个请求一个响应、然后关闭。好处是实现简单、服务端不用维护会话状态、异常清理容易；代价是每次建连有开销。对校园失物招领这种低频操作场景，短连接的简单性更重要。

**Q3：反射命令分发比 `if-else` 好在哪？**
A：服务端用 `@RemoteCommand` 注解标注处理方法，启动时扫描并建立'命令名 → 方法'的映射，请求来了直接 `Method.invoke()`。好处是**新增命令完全不用改网络层和分发层**，加一个带注解的方法就行，符合开闭原则；`if-else` 每加一个命令都要改分发代码，分支越多越难维护。

**Q4：`ConcurrentHashMap` 和 `synchronized` 各解决什么问题？**
A：它们解决的不是同一层的并发。`ConcurrentHashMap` 解决的是**不同记录之间**的并发读写安全，让多个线程能并行操作不同记录。`synchronized` 解决的是**同一条记录内部**的状态流转原子性，比如认领时'判断状态 + 写认领人'必须一起完成。分两层是为了锁的粒度尽量小。

**Q5：`serialVersionUID` 有什么用？**
A：它是序列化的版本标识。反序列化时 JVM 会比对这个值，不一致就抛 `InvalidClassException`。我们固定为 `1L`，这样即使后来删掉了描述字段，旧的 `.dat` 快照文件仍然能读出来，不会因为类改了就直接读不了——当然被删字段读出来就是默认值。

**Q6：`Math` 类在你们项目里用在哪？**
A：用在统计模块算'已认领率'，`Math.round(已认领数 * 100.0 / 总数)`，因为整数除法会丢精度，要先转成浮点再四舍五入。原来还有一处 `Math.min` 做描述截断的边界保护，随描述字段一起取消了。演示时如果想让认领率出现 33%、50% 这类需要四舍五入的值，可以先删几条记录再统计——输出里 `已认领率：14` 就是这么来的。

> 提醒：如果老师追问"只有一处 `Math` 够不够"，可以说 `Math.round` 之外项目里还用了 `Math` 的 `min`/`abs` 等思路，但目前代码里确实只有 `Math.round` 一处。回答要如实，不要夸大——如实说'精简后主要保留在统计的取整上'即可。

**Q7：实体类为什么要自己校验，不让业务层校验？**
A：为了让'非法对象根本构造不出来'。校验写在构造器里，只要对象存在就一定是合法的，业务层不用层层判空；而且报错信息带字段名，能直接返回给用户。这比校验散落在各处的写法更可靠——一个地方漏了就会让脏数据进到仓库里。

**Q8：你在这个过程中学到了什么？**
A：两个技术上的收获：一是知道 `SimpleDateFormat` 不能多线程共享、`DateTimeFormatter` 可以，这是踩过坑才记住的；二是理解了并发问题不是'加锁就行'，而要判断锁的粒度——我们分两层加锁，就是为了在保证正确性的同时不牺牲并发性能。另外团队协作上，文档和代码分分支提交、改公共字段前先沟通，这两条让我们基本没出现过返工。
